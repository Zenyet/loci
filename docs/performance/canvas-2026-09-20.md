# Canvas 性能检查 · 2026-09-20

连续缩放的主要开销来自每帧重复绘制阴影、文件夹渐变、文字及其底板。原有实现已经使用按需 rAF 和屏幕外裁剪，也没有在滚轮事件中触发 React 重渲染，但这不足以抵消 Canvas 光栅化开销。优化后的三个测试规模均达到本次环境的 60 Hz 帧率上限。

本机 Apple M4 Pro（16 核 GPU），Chrome 153.0.8010.52，ANGLE Metal，硬件 Canvas/rasterization 开启。使用隔离 Chrome 配置、headless 模式、1440×900 CSS 像素的画布、DPR 2。浏览器空场景 rAF 校准约 59.88 Hz。优化前版本为 `a632f5df21d046814bf5f391e9567c69f8a3391e` 中的 `render.ts`。

每个规模预热 90 帧，之后记录约 4 秒连续缩放和平移，重复 3 轮，表格取每轮统计值的中位数。场景包含 20% 文件夹、64 种 favicon、部分字母头像、N−1 条自动边，缩放范围 0.3–1.25。此范围用来覆盖缩小后大量节点同时可见的压力场景。基准使用固定布局，不把物理模拟与绘制混在一个数字里。

| 节点数 | FPS：前 → 后 | 帧间隔 P95 / ms | 渲染主线程 CPU | GPU 进程 CPU | 整机 GPU 利用率 |
| --- | --- | --- | --- | --- | --- |
| 100 | 47.8 → 60.0 | 33.4 → 16.7 | 12.8% → 7.9% | 89.1% → 16.3% | 60.7% → 32.3% |
| 500 | 26.2 → 60.0 | 116.6 → 16.7 | 11.4% → 13.2% | 90.9% → 27.8% | 65.1% → 39.5% |
| 2000 | 21.4 → 60.0 | 166.6 → 16.7 | 11.7% → 16.9% | 89.7% → 32.7% | 65.4% → 41.7% |

优化后的 9 个采样区间全部没有超过 1.5 倍刷新周期（约 25 ms）的帧。2000 节点绘图指令提交耗时 P95 从约 12.3 ms 降至 3.0 ms。FPS 是 rAF 回调间隔测量，并非显示器逐帧呈现追踪。

CPU 口径：主线程使用 CDP `Performance.TaskDuration` 差值；GPU 进程使用 `SystemInfo.getProcessInfo` 的 CPU 时间差值；100% 均相当于占满一个 CPU 核。GPU 进程 CPU 不是显卡利用率。大场景优化后主线程每秒工作量略升，因为交付的帧数接近原来的三倍；GPU 进程开销显著降低。

GPU 硬件口径：macOS `AGXAccelerator/PerformanceStatistics/Device Utilization %`，每 250 ms 采样，取各轮均值的中位数。它包含桌面合成及其他应用，不能全部归因于 Loci，也不能与进程 CPU 百分比相加。

已实施的修改：

- 将文件夹、计数徽标、favicon、字母头像、文字与底板缓存为离屏位图。同一文件夹图形与徽标分别复用，避免为不同计数复制整张图形。
- 缓存按分辨率分档，放大后分批更新清晰度，滚轮停止后补齐尚未完成的缓存。构建工作采用每帧约 2 ms 的软预算，单次操作仍可能超出该预算。
- 缓存最多保留 800 万像素、2048 个条目，约 32 MB 的 RGBA 原始像素；主画布最多 600 万像素，约 24 MB。浏览器纹理副本、对象及驱动开销另计。缓存不会让正在使用的条目相互反复驱逐，卸载时释放 backing store。
- 对至少 200 个节点的图谱，在缩放低于 0.7 时隐藏小于约 10px 的普通标题与计数徽标，保留悬停、拖拽、搜索命中和聚焦范围中的标题。小图谱保留原来的标签显示方式。这是有意的细节层级调整。
- 合并不变的边列表，复用节点 ID 集合，淡入淡出结束后跳过整图透明度计算；文字缓存满时逐项淘汰，避免全量清空后的测量尖峰。
- 同色边直接使用颜色，去掉无效渐变和逐边重复的线型设置。
- 同一帧内的滚轮事件共用一次布局读取；兼容像素、行、页三种 deltaMode；缩放到边界后惯性滚轮不再触发重绘。
- 按住平移或连线手势但不移动时停止空转；按住节点不动时物理模拟也能冷却，继续移动时再加热；隐藏文档不再排入新的绘图帧，空图谱不再等待无意义的模拟冷却。
- favicon 加载并发限制为 6，切换集合或卸载时取消队列、请求回调及超时；缓存 URL 的 origin 解析结果，避免每帧重复构造 URL。

物理模拟单独测量：优化版 100／500／2000 节点 tick 的 P95 分别约为 0.1／0.9／4.4 ms；测试没有手动连接边，不代表最坏拓扑。缩放已冷却的图谱不会重新启动模拟。活跃拖拽需要额外承担模拟成本，不能直接套用固定布局的 FPS。

验证：`npm run check` 通过，包括 `check:ui`、TypeScript、53 个测试文件中的 360 个测试及生产构建；浏览器中检查了文件夹导航、滚轮放大、异步图标加载、文字清晰度。新增回归覆盖缓存容量与释放、分批构建、暂停和恢复绘制、滚轮布局合并、缩放边界、图标并发及取消、静止拖拽冷却、密集图谱标签策略、超大画布像素预算。构建仍有现有 Anthropic SDK 的 Node 模块浏览器兼容警告，未导致失败。

复跑命令（Node 22+，本机 Chrome；Linux 可设置 `CHROME_PATH`）：

```sh
BENCH_RUNS=3 BENCH_OUTPUT=/tmp/loci-canvas-after.json npm run bench:canvas
BENCH_RUNS=3 BENCH_BASELINE_REF=a632f5df21d046814bf5f391e9567c69f8a3391e BENCH_OUTPUT=/tmp/loci-canvas-before.json npm run bench:canvas -- --baseline
npm run bench:canvas -- --headed
```

`--baseline` 仅替换绘制模块以便对照，默认读取 HEAD，可用 `BENCH_BASELINE_REF` 固定旧提交。`--headed` 可在实际显示器上重新校准刷新率；本次没有验证 120/144 Hz 满帧、所有缩放范围、超大或稠密手动边拓扑，也没有将这些结果外推到其他设备。首屏冷缓存、图标网络加载及真实扩展数据不包含在预热后的绘制基准中。

原始结果：[优化前](canvas-2026-09-20-baseline.json)、[优化后](canvas-2026-09-20-optimized.json)。缓存策略亦与 [MDN Canvas 优化建议](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas) 中减少重复绘制、阴影和文字光栅化的建议一致。
